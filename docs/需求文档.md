## 1. 项目概述与产品定位

### 1.1 产品定位
一个面向中文用户的**东西方玄学占卜 Web 应用**，核心价值主张为"塔罗不是预言，而是镜子"，将塔罗、紫微斗数、四柱八字、西方占星、东方术数（小六壬/六爻/梅花易数/大六壬/奇门遁甲）整合为统一的占卜体验。

### 1.2 目标用户
- **占卜爱好者**：对塔罗/星座/命理有兴趣，寻求指引与陪伴的普通用户
- **灵性探索者**：关注内在成长、冥想、能量与神秘学关联的用户
- **困惑决策者**：在爱情、事业、财运等具体事项上需要心理疏导与方向建议的用户

### 1.3 产品原则（现有代码中体现的业务理念）
1. **先接情绪、再给信息**：解读开场先共情用户情绪，复述问题以示"被听见"
2. **解读必须落到具体生活场景**：每个解读包含"生活行动建议"与"警示"，而非泛泛而谈
3. **中西合璧**：塔罗解读可叠加东方术数起卦，形成"组合占卜"
4. **结果留痕**：每次占卜记录保存，形成个人占卜历史

## 2. 现状盘点（重构前基线）

### 2.1 两代代码库并存

| 维度 | 旧版 divination-app/ | 新版根目录 src/ + server/ |
|---|---|---|
| 技术栈 | 原生 HTML/JS/CSS（约 2.4 万行） | React 18 + TS + Vite 6 + Express（约 1.1 万行） |
| 塔罗 | 完整：简化 78 张牌数据 + LLM AI 解读 | 完整：78 张牌（含神秘学关联）+ 规则化语义解读 |
| 紫微斗数 | 完整排盘 + 城市/真太阳时 + LLM 解读（1473 行） | 占位页（"开发中"） |
| 四柱八字 | 完整排盘 + 五行十神 + LLM 解读（796 行） | 占位页 |
| 西方星盘 | 完整星盘 + 天文计算库 + LLM 解读（780 行） | 占位页 |
| LLM 引擎 | 多 Provider（Gemini/Groq/DeepSeek/Qwen/自定义/Puter/本地） | 无（纯规则引擎） |
| 用户体系 | 注册/登录 + 个人记忆系统（localStorage） | 无 |
| 农历/天文库 | lunar.js（8538 行） | 无 |

> **重构含义**：新版是"以塔罗为核心"的重写版，但紫微/八字/星盘的**完整业务逻辑与数据资产全部沉淀在旧版**，重构时必须将旧版能力迁移/融合进新版架构，而非从零开发。

### 2.2 新版技术架构

```
浏览器 (React SPA)
  ├── src/pages/*       页面层（路由 8 条）
  ├── src/components/*  通用组件（星空背景/塔罗牌/导航）
  ├── src/stores/       zustand 全局状态（当前解读/组合结果）
  ├── src/services/api   API 客户端（fetch，/api 前缀）
  ├── src/utils/*       业务引擎（引擎实为服务端执行，前端为重复副本）
  └── src/data/*        静态数据（78 张牌/17 牌阵/场景语料）

服务端 (Express, :3001)
  ├── src/routes/tarot.ts    塔罗路由（draw/interpret/analyze/stream）
  ├── src/utils/*            解读引擎（tarotEngine/semanticAnalyzer）
  └── src/data/*             与前端重复的数据副本

Vite dev proxy: /api → http://localhost:3001
```

| # | 问题 | 影响 |

| P10 | **历史记录无详情页**："重新查看"仅跳转 /tarot，无法回看当时牌面与解读 | 功能半成品 |

### 5.2 M2 塔罗占卜（核心业务）

#### 5.2.1 占卜主流程（M2-F1，P0，✅ 已实现）

```
输入问题 → 选择分类(8类) → 选择牌阵(预设/自定义) → [随机抽牌 | 手动选牌]
   → 翻牌 → 生成解读(7段) → 逐段播放 → [可选]组合占卜 → 保存记录
```

**业务规则**：
1. **问题输入**：必填（空白不可开始占卜）；无长度限制校验（现状）
2. **问题分类**（8 个 UI 分类 + 类型定义共 10 个）：爱情/事业/财运/健康/学业/家庭/灵性/综合（类型另有 friendship/travel 未暴露 UI）
3. **牌阵选择**：17 个预设 + 用户自定义；默认选中第一个预设
4. **随机抽牌**：洗牌后按牌位顺序抽取，**逆位概率 30%**
5. **手动选牌**：从 78 张牌中选择，可选正/逆位，需选满牌位数才可解读；支持搜索与花色筛选
6. **解读生成**：调服务端 POST /api/tarot/interpret，返回结构化解读
7. **记录保存**：占卜成功后写入历史（localStorage，上限 100 条）

**验收要点**：必填校验、抽牌动画（1.5s 模拟延迟）、解读失败时给出用户可见提示（现状缺失）。

#### 5.2.2 语义分析（M2-F2，P0，✅ 已实现）

对用户问题进行多维度分析，作为解读素材：

| 维度 | 取值范围 |
|---|---|
| 场景 scene | love/career/wealth/study/health/family/friendship/spiritual/travel/general（关键词加权匹配） |
| 情绪 emotion | anxious/hopeful/confused/lost/grateful/calm/angry/sad/curious |
| 时态 tense | past/present/future/hypothetical/ongoing |
| 对象 subject | self/other/mutual/third-party |
| 深度 depth | surface/mid/deep |
| 问题类型 questionType | decision/prediction/reason/advice/mindreading/timing/general |
| 关键实体 | person（前任/老板/同事等）/ event（分手/跳槽等）/ time（最近/明年等） |
| 潜台词分析 | 真实问题（realQuestion）、情绪需求（emotionalNeed）、回应类型（comfort/direction/confirmation/warning） |
| 强度/置信度 | intensity 0-1、confidence 0-1 |

#### 5.2.3 解读结构（M2-F3，P0，✅ 已实现）

解读由 7 个固定段落组成（每段含标题/内容/建议展示时长）：

| 段序 | 类型 | 标题 | 内容要点 |
|---|---|---|---|
| 1 | opening | 开场引言 | 情绪共情 + 复述问题 + 点破核心关切 + 介绍牌阵 + 引导语 |
| 2 | overview | 综合指引 | 能量格局（元素占比/大小阿卡纳/正逆位比例）、牌间关系（因果/递进/张力/互补）、核心一句话、整体判断 |
| 3 | card ×N | 逐牌解读 | 每张牌：正/逆位、牌面故事、核心意象、落在牌位的含义、对应生活领域（按场景映射）、心理照见、建议、警示、关键词 |
| 4 | esoteric | 神秘学视角 | 主导元素、行星、卡巴拉质点、炼金阶段、灵数总和归约（%22） |
| 5 | life-action | 生活行动 | 按场景给出 3-7 条具体可执行建议（场景语料库 lifeContext） |
| 6 | warning | 警示提醒 | 按场景给出 3-7 条禁忌/注意（场景语料库） |
| 7 | summary | 总结收束 | 核心讯息、时间线展望（短/中/长）、祝福收尾 |

**生活领域映射规则**：love→爱情、career→事业、wealth→财运、health→健康、其余场景（study/family/friendship/spiritual/travel/general）→ growth 成长领域。

#### 5.2.4 解读展示与播放（M2-F4，P0，✅ 已实现）

- 打字机逐字效果，按段落顺序自动播放（速度可调 30-100ms/字）

- 语义识别结果以标签形式展示（场景/情绪/时态/对象）
- 服务端已提供 **SSE 流式接口**（/api/tarot/interpret/stream 逐字推送），前端客户端 streamInterpret 已封装但**未启用**——重构时应启用流式体验或移除冗余代码

#### 5.2.5 塔罗牌数据模型（M2-F5，P0，✅ 数据已完备）

78 张牌完整数据（22 大阿卡纳 + 56 小阿卡纳），每张牌字段：

| 字段 | 说明 |
|---|---|
| id/name/nameEn | 编号与中英文名 |
| arcana/suit/number | 大/小阿卡纳、花色（权杖/圣杯/宝剑/星币）、序号 |
| keywords | 3-5 个关键词 |
| meanings | 正位/逆位含义 |
| deepMeaning | 核心主题/心理/灵性/阴影 + 六生活领域（爱情/事业/财富/健康/成长）+ 建议/警示 |
| imageSymbols/story | 牌面意象清单与故事 |
| astrology | 星座/行星/元素 |
| kabbalah | 卡巴拉路径/质点 |
| alchemy | 炼金阶段/元素 |
| numerology | 灵数含义 |
| image | 图片（当前为占位） |

> **重构注意**：前端 src/data/tarotCards.ts 与后端 server/src/data/tarotCards.ts 已不一致（diff 有差异），需以单一数据源收敛。

## 9. 重构建议与路线图

### 9.1 架构目标
1. **单一数据源**：牌数据/牌阵/引擎收敛到一处（推荐 monorepo 共享包或服务端唯一真源）
2. **能力融合**：新版 React 壳 + 旧版命理/LLM 能力迁移（排盘逻辑可先以纯函数/worker 形式复用，再逐步 TS 化）
3. **数据上云**：引入用户体系与云端存储，localStorage 仅作离线兜底
4. **模块化**：TarotPage 拆分；解读引擎与 UI 解耦；新增"解读 Provider"抽象（规则/LLM 可切换）
5. **专业度升级**：真实天文/历法计算（复用 lunar.js）、完整术数算法

### 9.2 分期路线图（建议）

| 阶段 | 范围 | 目标 |
|---|---|---|
| **第一期（P0）** | 代码收敛与体验修复 | 消除前后端重复、单一数据源；启用 SSE 流式解读；修复历史详情/记录完整保存；统一错误处理；TarotPage 拆分 |
| **第二期（P1）** | 用户与命理核心 | 用户体系 + 数据上云；迁移紫微、八字（含 lunar.js 历法）；LLM 解读引擎接入（多 Provider） |
| **第三期（P2）** | 扩展与商业化 | 星盘迁移；组合占卜算法补全（64 卦/八门九星全量）；会员/付费能力；真实星象数据 |

### 9.3 需求决策点（需产品确认）
1. 组合占卜的起卦方式：纯时间 vs 交互式（用户参与掷卦）？
2. 解读生成策略：纯规则（现状）/ 纯 LLM / 混合（推荐：规则保底 + LLM 增强）？
3. 用户体系：手机号/邮箱/微信登录？是否需要付费能力预留？
4. 紫微/八字输入：是否需要真太阳时城市校正（旧版已支持，推荐保留）？
5. 历史记录上限：上云后是否无限保留？是否需要导出/分享能力？
