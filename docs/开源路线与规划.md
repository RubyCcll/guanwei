## 0. 一句话战略

观微的开源位是**「真算派全栈标杆」**：排盘不靠 LLM 猜、AI 解读有硬闸门、MIT 可商用。
后续所有动作围绕立住三块招牌：**评测闭环（质量事实标准）→ 开放分发（生态增长）→ 断语库深度（学术护城河）**，最终衔接 B2B2C 商业化（开源引流 + 命理师工具收费）。

## 2. 方向选择：从调研中筛出的 4 个主方向

> 选择逻辑：报告「最该补的三块」（评测闭环 / 开放分发 / 断语库深度）+ 劣势#1「绕开 iztro 事实标准」的应对。全部为**增量开发，不动现有引擎与架构**。

### 方向 A · 排盘精度基准 + iztro 生态兼容层（借势）
- **调研依据**：劣势#1（iztro 4073★ 事实标准，观微自研引擎借不到生态红利）；劣势#2（openfate 有 24 节气精确边界 + 反推八字；ichingshifa 是六爻纳甲正确性基准）
- **做法**：
  1. 建**公开排盘校验基准集**：用 ichingshifa（六爻纳甲）、openfate（节气边界）、iztro（紫微盘）三方互验观微盘面，沉淀为回归测试集；
  2. 引擎输出层增加 **iztro 盘面 JSON 兼容格式**，让观微盘面可被 iztro 生态工具（react-iztro 渲染等）直接消费 —— 不换引擎、借生态红利。
- **交付物**：`tests/benchmarks/` 基准集；`shared/core` 输出适配层
- **工作量**：中（适配层 2-3 天；基准集长期积累）
- **风险**：低（纯增量）；需跟进 iztro 格式变更

### 方向 B · AI 解读评测闭环：接入 MingLi-Bench（稀缺护城河）
- **调研依据**：劣势#3（无 AI 解读评测）；P0#1。MingLi-Bench 是全行业**唯一公开** LLM 命理评测基准（2314★，160 道命理师大赛真题 MCQ，原生支持 DeepSeek + iztro 盘注入）
- **做法**：
  1. 建评测 harness：`divineId → 盘面注入 → Agent 管线解读 → MCQ 判分 → 回归报告`；
  2. 与现有 `ai_fail_logs` 打通，形成**「评测驱动 prompt 迭代」正循环**；
  3. 首轮基线报告公开到 `docs/evals/`，作为对外可讲的质量证据。
- **交付物**：`server/scripts/eval/` harness + 基线报告
- **工作量**：中（harness 3-5 天 + 首轮基线）
- **风险**：低；MCQ 与观微报告结构的字段映射需打磨

### 方向 C · 开放分发：MCP Server + Agent Skill + REST API
- **调研依据**：劣势#4；P0#2。taibu/mingyu/Horosa-skill/liki 均已把排盘做成 MCP/Skill 卖给 Claude Code/Cursor 等外部 agent 生态，是**赛道 2026 的增长抓手**；观微目前是封闭 Web 应用
- **做法**：从 shared/core **单一算法副本**封装三种分发形态（成本低、杜绝引擎分叉）：
  1. `mcp-server/`：MCP 工具 `paipan / interpret`（stdio + SSE）；
  2. `skill/`：Claude Code / Cursor Agent Skill（对齐赛道 Skill 形态）；
  3. REST API：`/api/v1/paipan` 等只读排盘接口，API key + 配额闸门（直接复用已预留的 plan_tier/quota 字段）。
- **交付物**：`mcp-server/`、`skill/`、`server/routes/api-v1`
- **工作量**：中-大（MCP 3-5 天，Skill 1-2 天，API 2-3 天）
- **风险**：中（API 涉及成本与合规，首期只开放排盘、AI 解读走配额）

### 方向 D · 断语库 + 古籍引证闭环 + 考时校准（学术深度）
- **调研依据**：P0#3；liki 模式（597 条断语**每条带古籍原文** + 上下文因子消冲突 + 考时校准）；观微古籍页目前只是背景展示
- **做法**：
  1. **断语库**（结构化：断语 + 古籍原文出处 + 适用因子 + 消冲突规则），排盘 → 断语匹配 → AI 解读必须引用；
  2. **古籍引证闭环**：AI 报告中的引用可点击回跳古籍原文页（古籍从展示升级为证据链）；
  3. **考时校准**：用户回填事件，系统用事件反推核对断语（排盘 → 断语 → 事件的三方印证）。
- **交付物**：`shared/core/data/duanyu` 语料（首批 1-2 术 100-200 条）、古籍引证链路、`events` 表 + 校准流程
- **工作量**：大（语料审校是长线；链路开发 1-2 周）
- **风险**：中（语料质量与审校成本；可先用 1-2 术小步验证）

### 待命方向（P1/P2，不在本轮主线）
| 方向 | 对标 | 触发条件 |
|---|---|---|
| 忠实性校验器（逐句判 supported/invented/contradicted） | Horosa | M1 评测闭环跑通后 |

| 移动端 / PWA | taibu 三端 | 迭代计划已有，P1 |

| 安全护栏（自伤信号协议、危机降级、报告谱系） | tarot-skill / vedic | 用户量上来后 P2 |

### 明确不做（守住定位）
- ❌ 不追「LLM 猜盘」式快速变现（chatgpt-tarot 模式）——与真算派定位冲突
- ❌ 不做桌面端（Horosa 是 AGPL 技术天花板，Web + PWA 更合适、维护成本低）
- ❌ 不把 Skill 当主形态——观微是全栈应用，Skill/MCP 只是分发渠道
