## 5.5 地理编码与真太阳时（八字 / 紫微 / 星盘共用）

### 5.5.1 出生地点输入（省市县区三级）

- 输入面板组件 LocationPicker：省 → 市 → 县/区 三级级联下拉
- 数据集 regionData.ts：内置中国行政区划 → 经纬度（首期覆盖 34 省级 + 333 地级 + 主要县区，静态 JSON，随包发布，离线可用）
- 解析结果：{ province, city, district, lng, lat, timezone }，默认东八区
- 输入面板同步展示解析出的经纬度与真太阳时校正预览（如：北京时间 08:30 → 校正后 08:12）

### 5.5.2 真太阳时算法（trueSolarTime.ts）

```ts
// 平太阳时：北京时间 + 经度修正（东经120°为基准，每1°差4分钟）
localMeanTime = beijingTime + (lng - 120) * 4 / 60  // 小时

// 均时差 EoT（简化公式，精度 ±1 分钟，足以定时辰）
B = 2π * (N - 81) / 364            // N = 一年中的第几天
EoT = 9.87 * sin(2B) - 7.53 * cos(B) - 1.5 * sin(B)  // 分钟

// 真太阳时
trueSolarTime = localMeanTime + EoT / 60  // 小时

// 时辰判定：按真太阳时小时数 → 时辰序（23:00-00:59 子时…）
hourIndex = floor(((trueSolarHour + 1) % 24) / 2)
```

- **八字**：时柱以真太阳时定 hourIndex（子时边界 23:00 为日柱换日依据）；年柱/月柱用精确节气（lunar-typescript）
- **紫微**：时辰以真太阳时校正后再排盘（影响命宫）
- **星盘**：上升点 ASC 改用本地恒星时 LST 计算：
  - GST（格林尼治恒星时）由儒略日近似：GST = 6.697375 + 0.0657098242 * JD + UT
  - LST = GST + lng / 15（小时），ASC 黄经由 LST 推得（一期实现 LST → 上升星座近似映射，二期精确化）
- 出生地点同时影响**夏令时处理**（中国 1986-1991 年夏令时记录表内置，可开关）

### 5.5.3 校验用例（新增）

| 用例 | 期望 |
|---|---|
| 北京（116.40E）正午 12:00 → 真太阳时 ≈ 12:00±1min | 时差极小 |
| 乌鲁木齐（87.62E）北京 12:00 → 真太阳时 ≈ 9:50 | 经度修正生效 |
| 2024-02-03 立春前 vs 02-05 立春后 年柱切换（配合精确节气） | 癸卯 / 甲辰 |
| 1986-05-04（夏令时）→ 校正为标准时 | 夏令时表生效 |

## 5.6 万年历黄历与每日星相（almanac / daily）

### 5.6.1 万年历黄历（封装 lunar-typescript）

- lunar.ts：公农历互转、农历日期、干支（年/月/日/时）、生肖、星座、二十四节气（精确）、月相
- huangli.ts：黄历宜忌（宜：祭祀/出行/… 忌：…）、吉神凶煞、冲煞生肖、彭祖百忌
- 用途：首页今日黄历面板；各术排盘的精确节气/干支（八字月柱、奇门局数、大六壬月将全部改用精确节气）

### 5.6.2 每日星相 / 每日运势 / 每日星座（daily.ts）

| 能力 | 实现 | 个性化 |
|---|---|---|
| 每日星相 | 当日行星黄经（共享 astrology 近似算法）+ 月相 + 节气 + 黄历宜忌 | 无 |
| 每日运势 | 规则模板（当日天象）+ 用户星盘交叉 | 未登录：按当日太阳星座通用版 |

- **用户出生信息（UserProfile）**：birthDate、birthHour、location（省市区+经纬度）、gender；登录后从服务端读取，前端各术输入面板与首页自动预填
- 首页布局新增：今日黄历（宜忌+节气+月相）与今日星运（按登录用户个性化）两块面板

### 5.6.3 开源库评估

- lunar-typescript（6tail）：开源许可，支持公农历互转/节气/黄历/干支/星座，TS 原生，前后端通用 → **选定**，替代手写节气近似与农历转换
- 城市经纬度：首期内置精简数据集（省市区→经纬度），数据来源标注（公开地理数据整理）

## 6. AI 解读服务设计

### 6.1 服务端职责（Key 不下发前端）

```
POST /api/ai/interpret           # 非流式（保底）
POST /api/ai/interpret/stream    # SSE 流式（优先）

req: { artId, question?, resultRaw(JSON), semantic?, history?[] }
res: { provider, sections:[{title,content}], disclaimer }
```

### 6.2 Provider 适配层（移植自原始项目 llm-engine-v6.js）

```ts
interface LLMProvider {
  id: 'gemini' | 'groq' | 'deepseek' | 'qwen' | 'custom' | 'local';
  chat(messages, opts): AsyncIterable<string>; // 流式
}

// 配置存服务端（环境变量/配置文件），Key 绝不进入前端
// 降级链：主 Provider → 备 Provider → 规则模板解读
// （shared/core/engine/ruleFallback.ts，由原始项目 tarotEngine 泛化）
```

### 6.3 提示词构建（promptBuilder.ts）

1. **系统人设**：按术别配置（如八字→"深谙子平术的命理师"），约束：引据古籍、语言温润、不作绝对化断言、结尾免责
2. **事实层**：resultRaw JSON（排盘结果）+ 该术规则简述
3. **问题层**：用户问题 + 语义分析摘要（场景/情绪/问题类型）
4. **记忆层**：用户近 5 条占问（术别+问题摘要），脱敏（剔除人名/地名）
5. **输出结构**：JSON 约束 sections[{title,content}]，服务端解析后按 SSE 分节推送（沿用原始项目逐字推送模式）

### 6.4 降级与超时

- 流式 30s 无数据 → 切非流式重试 → 失败返回规则模板
- 用户可见文案："AI 未应机，已以古法规则为您解读"

## 7. 古籍与学馆数据设计

### 7.1 古籍（shared/core/data/classics.ts + 详情按需加载）


## 13. 语言风格规范（UI 提示 / 解读 / 古籍三层）

产品文案分三层，各层风格必须严格区分：

| 层 | 适用场景 | 风格 | 示例 |
|---|---|---|---|
| 古风提示层 | 界面提示：按钮、placeholder、hint、引导语、空态、面板标题、免责声明 | 文言/古风短句，克制雅致，用典而不晦涩 | 按钮：起卦、排盘、掐指一算；placeholder：默念所问，心念自随；hint：静心片刻，一念一事，同问不三占；空态：静候卦象，观微知著 |
| 现代解读层 | 排盘/起卦结果的占断说明、AI 解读正文 | 现代白话，直白清晰，有温度；避免过度玄学化表述，不绝对化断言 | 例：本卦为天泽履，提醒您行事谨慎、如履薄冰，宜先看清脚下再迈步 |
| 古籍话术层 | 古籍原文引用（古籍页、学馆引文、结果卡中的卦辞/掌诀原文） | 保持古籍原文话术，附现代注译；出处标注（书名·篇章） | 卦辞：「元亨利贞。天行健，君子以自强不息。」（《周易·乾卦》） |

**落地规则**：
1. 所有 UI 常量文案集中管理（src/i18n/strings.ts 或组件内常量表），古风文案带「古」注释标记，便于统一审校
2. 解读生成器（规则模板 + AI 提示词）一律输出现代语言；如需引经据典，以引用块形式单独呈现并标注出处（对应古籍话术层）
3. AI 提示词中明确三段式输出约定：现代解读正文 + 古籍引证（原文+注译）+ 免责尾注
4. 新页面/新组件评审时，按三层风格逐项检查
*本文档为 v2.0 技术基线；实施中如遇参考项目算法与原始项目资产冲突，以算法准确性与需求文档为准，并回更本档。*
